# Data Dictionary

เอกสารนี้อธิบายทุกตารางในฐานข้อมูล PostgreSQL ของระบบจัดการพอร์ตการลงทุน

- **ต้นฉบับของโครงสร้าง** คือ [`code/src/main/resources/schema.sql`](../code/src/main/resources/schema.sql) ถ้าเอกสารนี้กับไฟล์นั้นไม่ตรงกัน ให้ถือตาม `schema.sql`
- **ข้อมูลตัวอย่าง** อยู่ใน [`code/src/main/resources/data.sql`](../code/src/main/resources/data.sql) ได้แก่ผู้ใช้ demo, สินทรัพย์ 7 ตัว, ราคาย้อนหลัง, holding, เป้าหมายสัดส่วน และ watchlist
- **ภาพรวมความสัมพันธ์** ดูได้ที่ [`doc/diagrams/er-diagram.md`](diagrams/er-diagram.md)

ฐานข้อมูลมีทั้งหมด **13 ตาราง** มีความสัมพันธ์ครบทั้ง 1:1, 1:N และ N:M

| # | ตาราง | เก็บอะไร | ความสัมพันธ์หลัก |
|---|---|---|---|
| 1 | `users` | บัญชีผู้ใช้ | แม่ของ `user_profiles` (1:1), `portfolios` (1:N) |
| 2 | `user_profiles` | ข้อมูลเพิ่มเติมของผู้ใช้ | 1:1 กับ `users` |
| 3 | `portfolios` | พอร์ตการลงทุน | N:1 กับ `users`, แม่ของข้อมูลในพอร์ตทั้งหมด |
| 4 | `assets` | สินทรัพย์ที่ซื้อขายได้ | ถูกอ้างถึงจากหลายตาราง |
| 5 | `holdings` | สินทรัพย์ที่ถืออยู่ในพอร์ต | ตารางเชื่อม N:M `portfolios` ↔ `assets` ที่มีข้อมูลของตัวเอง |
| 6 | `transactions` | ประวัติซื้อ/ขาย/ปันผล | N:1 กับ `portfolios` และ `assets` |
| 7 | `price_history` | ราคารายวันของสินทรัพย์ | N:1 กับ `assets` |
| 8 | `market_indices` | ดัชนีตลาด (ใช้เทียบผลตอบแทน) | แม่ของ `index_price_history` |
| 9 | `index_price_history` | ค่าดัชนีรายวัน | N:1 กับ `market_indices` |
| 10 | `price_alerts` | การแจ้งเตือนราคา | N:1 กับ `portfolios` และ `assets` |
| 11 | `allocation_targets` | สัดส่วนเป้าหมายของแต่ละสินทรัพย์ในพอร์ต | N:1 กับ `portfolios` และ `assets` |
| 12 | `rebalance_logs` | ประวัติการรีบาลานซ์ | N:1 กับ `portfolios` |
| 13 | `user_watchlist` | หุ้นที่ผู้ใช้ติดตาม | ตารางเชื่อม N:M `users` ↔ `assets` |

### อ่านตารางอย่างไร

- **Null:** `N` หมายถึง NOT NULL และ `Y` หมายถึงเว้นว่างได้
- **Key:** `PK` คือ Primary Key, `FK → ตาราง` คือ Foreign Key, `UQ` คือเป็นส่วนหนึ่งของ UNIQUE constraint
- **ID:** ทุกตาราง (ยกเว้น `user_watchlist`) ใช้ `id BIGINT GENERATED BY DEFAULT AS IDENTITY` เป็น PK ฝั่ง JPA ใช้ `@GeneratedValue(strategy = IDENTITY)`
- **คอลัมน์ enum:** เก็บเป็นข้อความ (`@Enumerated(EnumType.STRING)`) ไม่ใช่ลำดับตัวเลข เพราะการเพิ่มค่าใหม่ใน enum จะไม่ทำให้ข้อมูลเดิมเพี้ยน
- **CHECK:** ทุกคอลัมน์ enum มี CHECK บังคับให้เก็บได้เฉพาะค่าที่มีใน enum ฝั่ง Java

## 1. `users`

บัญชีผู้ใช้สำหรับเข้าสู่ระบบ ยืนยันตัวตนด้วย JWT

| คอลัมน์ | ชนิด | Null | Key | Default / Check | คำอธิบาย |
|---|---|---|---|---|---|
| `id` | BIGINT | N | PK | identity | รหัสผู้ใช้ |
| `username` | VARCHAR(50) | N | UQ | — | ชื่อผู้ใช้ ห้ามซ้ำ |
| `email` | VARCHAR(100) | N | UQ | — | อีเมลสำหรับ login ห้ามซ้ำ |
| `password_hash` | VARCHAR(255) | N | | — | รหัสผ่านที่ hash ด้วย BCrypt (ไม่เก็บรหัสผ่านจริง) |
| `role` | VARCHAR(20) | N | | `USER`, `ADMIN` | สิทธิ์ของผู้ใช้ |
| `created_at` | TIMESTAMP(6) | N | | ตั้งโดย `@PrePersist` | วันเวลาที่สมัคร |

Constraints: `pk_users`, `uq_users_username`, `uq_users_email`, `ck_users_role`

## 2. `user_profiles`

ข้อมูลเสริมของผู้ใช้ แยกจาก `users` เพื่อให้ตารางบัญชีเก็บแค่ข้อมูลยืนยันตัวตน

| คอลัมน์ | ชนิด | Null | Key | Default / Check | คำอธิบาย |
|---|---|---|---|---|---|
| `id` | BIGINT | N | PK | identity | รหัสโปรไฟล์ |
| `user_id` | BIGINT | N | FK → `users`, UQ | ON DELETE CASCADE | เจ้าของโปรไฟล์ UNIQUE ตรงนี้ทำให้เป็น **1:1** |
| `risk_tolerance` | VARCHAR(20) | Y | | `LOW`, `MEDIUM`, `HIGH` | ระดับความเสี่ยงที่รับได้ (ใช้กับ Risk-based allocation) |
| `investment_goal` | VARCHAR(255) | Y | | — | เป้าหมายการลงทุน |
| `phone` | VARCHAR(20) | Y | | — | เบอร์โทร |

Constraints: `pk_user_profiles`, `uq_user_profiles_user_id`, `fk_user_profiles_user_id`, `ck_user_profiles_risk`

## 3. `portfolios`

พอร์ตการลงทุน ผู้ใช้หนึ่งคนมีได้หลายพอร์ต

| คอลัมน์ | ชนิด | Null | Key | Default / Check | คำอธิบาย |
|---|---|---|---|---|---|
| `id` | BIGINT | N | PK | identity | รหัสพอร์ต |
| `user_id` | BIGINT | N | FK → `users` | ON DELETE CASCADE | เจ้าของพอร์ต |
| `name` | VARCHAR(100) | N | | — | ชื่อพอร์ต |
| `base_currency` | VARCHAR(10) | N | | — | สกุลเงินหลักของพอร์ต เช่น `THB` |
| `created_at` | TIMESTAMP(6) | N | | ตั้งโดย `@PrePersist` | วันที่สร้างพอร์ต |

Constraints: `pk_portfolios`, `fk_portfolios_user_id` · Index: `idx_portfolios_user_id`

## 4. `assets`

สินทรัพย์ที่ซื้อขายได้ ใช้ร่วมกันทุกพอร์ต (master data)

| คอลัมน์ | ชนิด | Null | Key | Default / Check | คำอธิบาย |
|---|---|---|---|---|---|
| `id` | BIGINT | N | PK | identity | รหัสสินทรัพย์ |
| `symbol` | VARCHAR(20) | N | UQ | — | ชื่อย่อ เช่น `PTT`, `AAPL` ห้ามซ้ำ |
| `name` | VARCHAR(100) | N | | — | ชื่อเต็ม |
| `asset_type` | VARCHAR(20) | N | | `STOCK`, `ETF`, `BOND`, `MUTUAL_FUND`, `CRYPTO`, `CASH` | ประเภทสินทรัพย์ |
| `exchange` | VARCHAR(50) | Y | | — | ตลาดที่ซื้อขาย เช่น `SET`, `NASDAQ` |
| `price_source` | VARCHAR(20) | Y | | `YAHOO`, `SYNTHETIC` | แหล่งราคา: ดึงจาก Yahoo Finance หรือสร้างจำลอง |

Constraints: `pk_assets`, `uq_assets_symbol`, `ck_assets_type`, `ck_assets_price_source`

## 5. `holdings`

สินทรัพย์ที่ถืออยู่ในแต่ละพอร์ต เป็นตารางเชื่อม **N:M** ระหว่าง `portfolios` กับ `assets` แต่มีข้อมูลของตัวเอง (จำนวนหน่วย, ต้นทุนเฉลี่ย) จึงทำเป็น entity แยก ไม่ใช้ `@ManyToMany`

ค่าในตารางนี้คำนวณจาก `transactions` ทุกครั้งที่บันทึกธุรกรรม (`HoldingService.applyTransaction`)

| คอลัมน์ | ชนิด | Null | Key | Default / Check | คำอธิบาย |
|---|---|---|---|---|---|
| `id` | BIGINT | N | PK | identity | รหัส holding |
| `portfolio_id` | BIGINT | N | FK → `portfolios`, UQ | ON DELETE CASCADE | พอร์ตที่ถือ |
| `asset_id` | BIGINT | N | FK → `assets`, UQ | ON DELETE RESTRICT | สินทรัพย์ที่ถือ |
| `quantity` | NUMERIC(18,6) | N | | `>= 0` | จำนวนหน่วยคงเหลือ (6 ตำแหน่งรองรับคริปโตเศษหน่วย) |
| `avg_cost` | NUMERIC(18,4) | N | | `>= 0` | ต้นทุนเฉลี่ยต่อหน่วย (ถัวเฉลี่ยเมื่อซื้อเพิ่ม) |
| `updated_at` | TIMESTAMP(6) | N | | ตั้งโดย `@PrePersist/@PreUpdate` | อัปเดตล่าสุด |

Constraints: `pk_holdings`, `uq_holdings_portfolio_asset` (portfolio_id, asset_id), `fk_holdings_portfolio_id`, `fk_holdings_asset_id`, `ck_holdings_quantity`, `ck_holdings_avg_cost` · Index: `idx_holdings_asset_id`

## 6. `transactions`

ประวัติธุรกรรมทุกรายการของพอร์ต ใช้คำนวณ holding และผลตอบแทน

| คอลัมน์ | ชนิด | Null | Key | Default / Check | คำอธิบาย |
|---|---|---|---|---|---|
| `id` | BIGINT | N | PK | identity | รหัสธุรกรรม |
| `portfolio_id` | BIGINT | N | FK → `portfolios` | ON DELETE CASCADE | พอร์ตที่ทำธุรกรรม |
| `asset_id` | BIGINT | N | FK → `assets` | ON DELETE RESTRICT | สินทรัพย์ |
| `type` | VARCHAR(20) | N | | `BUY`, `SELL`, `DIVIDEND`, `DEPOSIT`, `WITHDRAWAL` | ประเภทธุรกรรม (`BUY`/`SELL` เปลี่ยนจำนวนหน่วยใน holding ส่วนประเภทอื่นไม่เปลี่ยน) |
| `quantity` | NUMERIC(18,6) | N | | `> 0` | จำนวนหน่วย |
| `price` | NUMERIC(18,4) | N | | `> 0` | ราคาต่อหน่วย |
| `executed_at` | TIMESTAMP(6) | N | | — | วันเวลาที่ทำธุรกรรม (บันทึกย้อนหลังได้ แต่ห้ามเป็นอนาคต ซึ่งตรวจที่ DTO) |

Constraints: `pk_transactions`, `fk_transactions_portfolio_id`, `fk_transactions_asset_id`, `ck_transactions_type`, `ck_transactions_quantity`, `ck_transactions_price` · Index: `idx_transactions_portfolio_executed` (portfolio_id, executed_at), `idx_transactions_asset_id`

## 7. `price_history`

ราคาปิดรายวัน (OHLCV) ของแต่ละสินทรัพย์ ใช้วาดกราฟ หาแนวรับ/แนวต้าน และคำนวณผลตอบแทน

| คอลัมน์ | ชนิด | Null | Key | Default / Check | คำอธิบาย |
|---|---|---|---|---|---|
| `id` | BIGINT | N | PK | identity | รหัสแถว |
| `asset_id` | BIGINT | N | FK → `assets`, UQ | ON DELETE CASCADE | สินทรัพย์ |
| `price_date` | DATE | N | UQ | — | วันที่ของราคา |
| `open` | NUMERIC(18,4) | N | | `> 0` | ราคาเปิด |
| `high` | NUMERIC(18,4) | N | | `> 0`, `high >= low` | ราคาสูงสุด |
| `low` | NUMERIC(18,4) | N | | `> 0` | ราคาต่ำสุด |
| `close` | NUMERIC(18,4) | N | | `> 0` | ราคาปิด |
| `volume` | BIGINT | Y | | — | ปริมาณซื้อขาย |

Constraints: `pk_price_history`, `uq_price_history_asset_date` (asset_id, price_date), `fk_price_history_asset_id`, `ck_price_history_positive`, `ck_price_history_range`

| `name` | VARCHAR(100) | N | | — | ชื่อดัชนี |

Constraints: `pk_market_indices`, `uq_market_indices_code`

## 10. `price_alerts`

การแจ้งเตือนเมื่อราคาถึงเป้า สถานะเปลี่ยนตาม State pattern: `PENDING → TRIGGERED → NOTIFIED` หรือ `PENDING → EXPIRED`

| คอลัมน์ | ชนิด | Null | Key | Default / Check | คำอธิบาย |
|---|---|---|---|---|---|
| `id` | BIGINT | N | PK | identity | รหัส alert |
| `portfolio_id` | BIGINT | N | FK → `portfolios` | ON DELETE CASCADE | พอร์ตที่ตั้ง alert |
| `asset_id` | BIGINT | N | FK → `assets` | ON DELETE RESTRICT | สินทรัพย์ที่ติดตามราคา |
| `condition` | VARCHAR(20) | N | | `PRICE_ABOVE`, `PRICE_BELOW` | เงื่อนไข: ราคาขึ้นถึง / ลงถึงเป้า |
| `target_price` | NUMERIC(18,4) | N | | `> 0` | ราคาเป้าหมาย |
| `status` | VARCHAR(20) | N | | `PENDING`, `TRIGGERED`, `NOTIFIED`, `EXPIRED`, `CANCELLED` | สถานะปัจจุบัน |
| `created_at` | TIMESTAMP(6) | N | | ตั้งโดย `@PrePersist` | วันที่สร้าง (ใช้ตัดสินว่าหมดอายุหรือยัง) |

Constraints: `pk_price_alerts`, `fk_price_alerts_portfolio_id`, `fk_price_alerts_asset_id`, `ck_price_alerts_condition`, `ck_price_alerts_status`, `ck_price_alerts_target_price` · Index: `idx_price_alerts_status`, `idx_price_alerts_portfolio_id`, `idx_price_alerts_asset_id`

## 11. `allocation_targets`

สัดส่วนเป้าหมายของสินทรัพย์แต่ละตัวในพอร์ต ใช้คำนวณ drift และรีบาลานซ์ (เป้ารวมของพอร์ตต้องได้ 100% ซึ่งตรวจใน Chain of Responsibility ก่อนรีบาลานซ์)

| คอลัมน์ | ชนิด | Null | Key | Default / Check | คำอธิบาย |
|---|---|---|---|---|---|
| `id` | BIGINT | N | PK | identity | รหัสแถว |
| `portfolio_id` | BIGINT | N | FK → `portfolios`, UQ | ON DELETE CASCADE | พอร์ต |
| `asset_id` | BIGINT | N | FK → `assets`, UQ | ON DELETE RESTRICT | สินทรัพย์ |
| `target_percent` | NUMERIC(5,2) | N | | `0 – 100` | สัดส่วนเป้าหมาย (%) |

Constraints: `pk_allocation_targets`, `uq_allocation_targets_portfolio_asset` (portfolio_id, asset_id), `fk_allocation_targets_portfolio_id`, `fk_allocation_targets_asset_id`, `ck_allocation_targets_percent` · Index: `idx_allocation_targets_asset_id`

## 12. `rebalance_logs`

บันทึกทุกครั้งที่สั่งรีบาลานซ์ พร้อมรายการคำสั่งซื้อขายที่ได้

| คอลัมน์ | ชนิด | Null | Key | Default / Check | คำอธิบาย |
|---|---|---|---|---|---|
| `id` | BIGINT | N | PK | identity | รหัส log |
| `portfolio_id` | BIGINT | N | FK → `portfolios` | ON DELETE CASCADE | พอร์ต |
| `method` | VARCHAR(20) | N | | `THRESHOLD`, `CALENDAR` | วิธีรีบาลานซ์ (Strategy ที่ใช้) |
| `triggered_at` | TIMESTAMP(6) | N | | ตั้งโดย `@PrePersist` | วันเวลาที่สั่ง |
| `details` | TEXT | Y | | — | สรุปคำสั่งซื้อ/ขายที่สร้างขึ้น |

Constraints: `pk_rebalance_logs`, `fk_rebalance_logs_portfolio_id`, `ck_rebalance_logs_method` · Index: `idx_rebalance_logs_portfolio_id` (portfolio_id, triggered_at)

## 13. `user_watchlist`

ตารางเชื่อม **N:M** ระหว่าง `users` กับ `assets` (หุ้นที่ผู้ใช้กดติดตาม) ไม่มีข้อมูลอื่นนอกจาก 2 FK ฝั่ง JPA จึงใช้ `@ManyToMany` + `@JoinTable` ใน `User` ได้ตรง ๆ โดยไม่ต้องมี entity ของตัวเอง

| คอลัมน์ | ชนิด | Null | Key | Default / Check | คำอธิบาย |
|---|---|---|---|---|---|
| `user_id` | BIGINT | N | PK, FK → `users` | ON DELETE CASCADE | ผู้ใช้ |
| `asset_id` | BIGINT | N | PK, FK → `assets` | ON DELETE CASCADE | สินทรัพย์ที่ติดตาม |

Constraints: `pk_user_watchlist` (user_id, asset_id), `fk_user_watchlist_user_id`, `fk_user_watchlist_asset_id` · Index: `idx_user_watchlist_asset_id`

## นโยบาย ON DELETE

| FK | ON DELETE | เหตุผล |
|---|---|---|
| `user_profiles.user_id` → `users` | CASCADE | โปรไฟล์ไม่มีความหมายถ้าไม่มีผู้ใช้ |
| `portfolios.user_id` → `users` | CASCADE | ลบบัญชีแล้วพอร์ตทั้งหมดของผู้ใช้ต้องหายตาม |
| `holdings`, `transactions`, `price_alerts`, `allocation_targets`, `rebalance_logs` `.portfolio_id` → `portfolios` | CASCADE | ข้อมูลทั้งหมดนี้เป็นของพอร์ตนั้น ลบพอร์ตแล้วไม่ควรเหลือแถวกำพร้า |
| `holdings`, `transactions`, `price_alerts`, `allocation_targets` `.asset_id` → `assets` | **RESTRICT** | สินทรัพย์ใช้ร่วมกันหลายพอร์ต ถ้าลบสินทรัพย์ไปพร้อมกับธุรกรรม ประวัติการเงินของผู้ใช้จะหายและมูลค่าพอร์ตเพี้ยน จึงให้ฐานข้อมูลปฏิเสธ |
| `price_history.asset_id` → `assets` | CASCADE | ราคาย้อนหลังเป็นข้อมูลอ้างอิงของสินทรัพย์ตัวนั้นเท่านั้น |
| `index_price_history.market_index_id` → `market_indices` | CASCADE | ค่าดัชนีเป็นของดัชนีนั้นเท่านั้น |
| `user_watchlist.user_id` / `.asset_id` | CASCADE | watchlist เป็นแค่ที่คั่นหน้า ไม่ใช่ข้อมูลการเงิน หายตามได้ทั้งสองฝั่ง |

ทดสอบกับ PostgreSQL 16 ด้วย `schema.sql` + `data.sql` แล้ว:

- ลบ asset `PTT` ที่ยังมี holding อยู่ ถูกปฏิเสธด้วย `fk_holdings_asset_id`
- ลบผู้ใช้ demo แล้ว portfolios, holdings, transactions, user_profiles และ user_watchlist หายตามทั้งหมด แต่ assets ทั้ง 7 ตัวยังอยู่ครบ

## Cascade และ Fetch ฝั่ง JPA

| ความสัมพันธ์ (Entity) | Fetch | Cascade | เหตุผล |
|---|---|---|---|
| `@ManyToOne` ทุกตัว (เช่น `Holding.asset`, `Transaction.portfolio`) | **LAZY** | ไม่มี | ค่าเริ่มต้นของ JPA สำหรับ `@ManyToOne` คือ EAGER ซึ่งทำให้ดึงแม่มาทุกครั้งแม้ไม่ได้ใช้ และเกิดปัญหา N+1 ตอนโหลดเป็นรายการ จึงตั้ง LAZY ทุกตัว ไม่ cascade ขึ้นไปหาแม่ เพราะลบลูกต้องไม่ลบแม่ |
| `Portfolio` → `holdings`, `transactions`, `priceAlerts`, `allocationTargets`, `rebalanceLogs` (`@OneToMany`) | LAZY | `ALL` + `orphanRemoval` | ข้อมูลลูกเป็นส่วนหนึ่งของพอร์ต (aggregate) ลบพอร์ตผ่าน JPA แล้วลูกหายตาม ตรงกับ ON DELETE CASCADE ในฐานข้อมูล |
| `User` → `profile` (`@OneToOne`) | LAZY | `ALL` + `orphanRemoval` | โปรไฟล์อยู่ไม่ได้ถ้าไม่มีผู้ใช้ |
| `User` → `portfolios` (`@OneToMany`) | LAZY | `ALL` + `orphanRemoval` | ลบบัญชีแล้วพอร์ตทั้งหมดหายตาม |
| `User` → `watchlist` (`@ManyToMany`) | LAZY | ไม่มี | เอาหุ้นออกจาก watchlist ต้องลบแค่แถวในตารางเชื่อม ห้ามลบตัว `Asset` |
| `Asset` | — | — | ตั้งใจไม่ทำ `@OneToMany` ย้อนกลับไปหา holdings/transactions/price_history เพราะ `price_history` มีหลายพันแถว และไม่มี use case ไหนต้องเดินจาก asset ไปหาลูก ถ้าต้องการให้ query ผ่าน repository แทน |

## Index

PostgreSQL สร้าง index ให้ PK และ UNIQUE อัตโนมัติ แต่**ไม่สร้างให้ FK** จึงเพิ่ม index ให้ FK ที่ถูกค้นบ่อย และให้ FK ที่ต้องตรวจตอนลบแม่ (RESTRICT/CASCADE ต้องสแกนตารางลูก)

| Index | คอลัมน์ | ใช้กับ query ไหน |
|---|---|---|
| `idx_portfolios_user_id` | `portfolios(user_id)` | แสดงรายการพอร์ตของผู้ใช้ (`findByUserId` + pagination) |
| `idx_holdings_asset_id` | `holdings(asset_id)` | ตรวจ FK ตอนลบ asset; ค้นตาม `portfolio_id` ใช้ `uq_holdings_portfolio_asset` ได้อยู่แล้วเพราะเป็นคอลัมน์แรก |
| `idx_transactions_portfolio_executed` | `transactions(portfolio_id, executed_at)` | ประวัติธุรกรรมของพอร์ตเรียงตามเวลา และคำนวณผลตอบแทนตามช่วงวันที่ |
| `idx_transactions_asset_id` | `transactions(asset_id)` | ตรวจ FK ตอนลบ asset |
| `idx_price_alerts_status` | `price_alerts(status)` | scheduler ค้น alert ที่ `PENDING` ทุกรอบ |
| `idx_price_alerts_portfolio_id` | `price_alerts(portfolio_id)` | แสดง alert ของพอร์ต |
| `idx_price_alerts_asset_id` | `price_alerts(asset_id)` | ตรวจ FK ตอนลบ asset |
| `idx_allocation_targets_asset_id` | `allocation_targets(asset_id)` | ตรวจ FK ตอนลบ asset |
| `idx_rebalance_logs_portfolio_id` | `rebalance_logs(portfolio_id, triggered_at)` | ประวัติรีบาลานซ์ของพอร์ตเรียงตามเวลา |
| `idx_user_watchlist_asset_id` | `user_watchlist(asset_id)` | ตรวจ FK ตอนลบ asset; ค้นตาม `user_id` ใช้ PK ได้อยู่แล้ว |
| `uq_price_history_asset_date` (UNIQUE) | `price_history(asset_id, price_date)` | ดึงราคาของสินทรัพย์ตามช่วงวันที่ และกันราคาซ้ำวันเดียวกัน |
| `uq_index_price_history_index_date` (UNIQUE) | `index_price_history(market_index_id, price_date)` | เหมือนด้านบน สำหรับดัชนี |

## Migration

| โปรไฟล์ | สร้างตารางอย่างไร | ข้อมูลตัวอย่าง |
|---|---|---|
| `dev` | Hibernate `ddl-auto: update` สร้าง/แก้ตารางจาก entity (ชื่อ FK/UNIQUE/index ตั้งไว้ใน annotation ให้ตรงกับ `schema.sql`) | `data.sql` |
| `prod` | Spring รัน `schema.sql` ก่อน แล้ว Hibernate `ddl-auto: validate` ตรวจว่า entity ตรงกับตาราง ถ้าไม่ตรงแอปจะไม่ start | `data.sql` |

ทั้ง `schema.sql` และ `data.sql` รันซ้ำได้ เพราะใช้ `IF NOT EXISTS` / `ON CONFLICT DO NOTHING` ทดสอบแล้วโดยรันสองรอบติดกันบนฐานข้อมูลเดียวกันโดยไม่มี error

## หลักการตั้งชื่อ

- ตารางเป็นพหูพจน์ แบบ `snake_case`
- FK ใช้ชื่อ `<ตารางแม่เอกพจน์>_id`
- Constraint ใช้ชื่อตามรูปแบบนี้ ชื่อจึงบอกได้ทันทีว่า error มาจาก constraint ไหน:
  - `pk_<ตาราง>`
  - `fk_<ตาราง>_<คอลัมน์>`
  - `uq_<ตาราง>_<คอลัมน์>`
  - `ck_<ตาราง>_<เรื่อง>`
  - `idx_<ตาราง>_<คอลัมน์>`
